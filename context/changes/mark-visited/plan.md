# Mark Resorts as Visited (S-04) Implementation Plan

## Overview

Let a signed-in user **mark and unmark resorts as visited directly from the
browse list**, with the visual state updating **in place (no full page reload)**
and the visited list kept **strictly private** to that user. This is the app's
**first real HTMX interaction**: `htmx.min.js` is already loaded in the shared
layout but nothing uses it yet, so this slice also establishes the in-place
partial-update pattern and the CSRF-token-delivery wiring that S-05 (Recommend)
reuses.

Roadmap: `S-04 / mark-visited`. PRD refs: **US-02** (mark a resort as visited),
**FR-005** (mark/unmark visited). Prerequisites **S-01** (account-authentication)
and **S-03** (resort-catalog-browse) are both done — every route added here is
gated by the existing authenticated security chain.

## Current State Analysis

- **No visited domain exists.** The modeled domains are `user`
  (`com.nextslope.user`), `resort` (`com.nextslope.resort`), and `profile`
  (`com.nextslope.profile`). There is no visited entity, repository, service,
  controller, template, or migration.
- **Migration baseline is `V1__create_users.sql`, `V2__create_resorts.sql`, and
  `V3__create_preference_profiles.sql`** (the last added by the S-02 profile
  slice). Flyway owns DDL; Hibernate runs `ddl-auto=validate`
  (`application.properties`). **The next migration is `V4__`.** A new table needs
  a matching JPA mapping verified on **both** H2 (PostgreSQL mode, local) and
  Postgres (Testcontainers/Neon).
- **A clean per-user-data precedent exists.** `PreferenceProfile`
  (`profile/PreferenceProfile.java:50`) stores a plain `user_id` `BIGINT` column
  (no `@ManyToOne`), is resolved only via `PreferenceProfileRepository.findByUserId`,
  and exposes **no id in any route** — so there is no addressable cross-user
  (IDOR) surface, only an isolation guarantee. The visited model follows the
  same "plain `user_id` FK, principal-scoped, no cross-user route" shape.
- **The principal carries only the email, not the user id.**
  `AppUserDetailsService` (`user/AppUserDetailsService.java:23-26`) builds a
  Spring `User` with `username = email`. `ProfileController.currentUserId()`
  (`web/ProfileController.java:78-82`) resolves the `userId` by
  `userRepository.findByEmail(EmailNormalizer.normalize(principal.getUsername()))`
  → `getId()`, throwing `401` when absent. This slice reuses that exact pattern.
- **CSRF is enabled and pinned.** `CsrfEnforcedTests` asserts a state-changing
  POST without a token returns `403` and with a token is accepted. HTMX POSTs
  must therefore carry the CSRF token. No token is delivered to JS today (all
  current forms use Thymeleaf's auto-injected hidden `_csrf` field).
- **Security auto-gates new routes.** `SecurityConfig.filterChain`
  (`config/SecurityConfig.java:50-54`) permits an explicit public list and
  `.anyRequest().authenticated()`. A new `/resorts/{id}/visited` route is
  authenticated with no config change; anonymous requests redirect to `/login`.
- **The browse list has no per-row action column.** `resorts/list.html` renders
  a `th:each` table (Name, Country, Top lift, Total slopes, Total lifts,
  Difficulty mix) with a `colspan="6"` empty row. The resort detail page also
  has no visited control (out of scope: list only).
- **The active flag matters.** `ResortController.detail` uses
  `findByIdAndActiveTrue(id)` → `404` for missing/inactive. The browse list
  shows only `findByActiveTrueOrderByCountryAscNameAsc()`. FR-013 requires a
  *deactivated* resort's existing visited references to keep working.
- **Test scaffolding is waiting for exactly this slice.**
  `AccessControlAssertions.assertWrongOwnerDenied`
  (`support/AccessControlAssertions.java:66-68`) and
  `OwnershipPatternIntegrationTests` both name "S-04 (visited)" as the slice that
  specializes the wrong-owner / isolation seam. `TwoUserIntegrationTestBase`
  persists user A, user B, and admin with real hashed passwords and a `loginAs…`
  helper returning an authenticated `MockHttpSession`.

### Key Discoveries:

- **Entity convention** (`User.java:23-57`, `Resort.java:22-29`, AGENTS.md): one
  package per domain, Lombok `@Getter/@Setter/@NoArgsConstructor/@AllArgsConstructor/@Builder`,
  JPA `@Entity` over a Flyway-created table, audit columns via Hibernate
  `@CreationTimestamp` (not DB defaults) for cross-engine parity. → New
  `com.nextslope.visited` package.
- **Portable DDL** (`V1`–`V3`): `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY
  KEY`, `BIGINT`, `TIMESTAMP`, `UNIQUE`, `NOT NULL` — parses identically on H2
  (PG mode) and Postgres. No FK to `resorts`/`users` is strictly required by the
  existing tables (none cross-reference), but a join table with a `UNIQUE
  (user_id, resort_id)` guard is the integrity anchor here.
- **Dual-engine verification** (AGENTS.md, `UserRepositoryPostgresTests`,
  `ResortRepositoryPostgresTests`): a `@DataJpaTest` slice for fast local checks
  plus a `@Testcontainers` real-Postgres repository test prove the migration +
  mapping on both engines; CI runs both.
- **Owner-scoped service pattern** (`PreferenceProfileService`): service methods
  take `userId` (never an arbitrary entity id), `@Transactional` for writes /
  `@Transactional(readOnly = true)` for reads. → `VisitedResortService` mirrors this.
- **Controller test pattern** (`ProfileControllerWebMvcTests`,
  `ResortControllerWebMvcTests`): `@WebMvcTest(controllers = X.class)` +
  `@Import({SecurityConfig.class, AppUserDetailsService.class})`, `@MockitoBean`
  the service + `UserRepository`, `@WithMockUser(username = "user")`, `.with(csrf())`
  on POSTs, assert anonymous → redirect `/login`.

## Desired End State

A signed-in user on `/resorts` sees, on every active resort row, a toggle
control: **"Mark visited"** when not visited, **"Visited ✓"** (with a subtle row
highlight) when visited. Clicking it POSTs to `/resorts/{id}/visited`, which
flips the state in the database and returns just the updated control fragment,
swapped in place via HTMX with no full page reload. The visited list is private:
no other user — including an admin — can read it through any product surface, and
one user's marks never affect another's. The change is verified by a dual-engine
repository test, a controller test (toggle, CSRF, auth, 404), and a two-user
isolation integration test.

### Verification of end state:

- `./gradlew test` is green (including the new Testcontainers Postgres repo test
  and the two-user isolation test).
- Manually on `/resorts`: marking a resort highlights its row and flips the
  button to "Visited ✓" without a reload; clicking again unmarks it; the state
  survives a hard refresh; a second user's account shows none of the first
  user's marks.

## What We're NOT Doing

- **No visited control on the resort detail page** — browse list only (US-02
  wording; detail-page toggle is a later nicety).
- **No "my visited resorts" listing/page** — marking/unmarking in place only.
- **No use of the visited data in recommendations** — S-05 consumes it; this
  slice only adds the minimal read queries S-05 will reuse.
- **No visited-count badge, navbar indicator, or sorting/filtering by visited.**
- **No bulk mark/clear-all.**
- **No account-deletion cascade** — S-07 owns removing visited rows on account
  deletion.
- **No detail-page or recommendation-card surfacing of "visited" state.**

## Implementation Approach

Three vertical phases, bottom-up so each is independently verifiable:

1. **Persistence** — `V4` migration + `VisitedResort` entity + repository, proven
   on both engines.
2. **Service + toggle endpoint + privacy** — owner-scoped service, the POST
   toggle returning a control fragment, and the mandatory two-user isolation
   guarantee.
3. **List UI + HTMX wiring** — the per-row control, the reusable fragment, and
   the one-time CSRF-token delivery to HTMX (reused by S-05).

The data model is a **dedicated join entity** `VisitedResort(user_id, resort_id,
created_at)` with `UNIQUE (user_id, resort_id)` — explicit, queryable, and the
natural home for "when marked" audit data, mirroring the lean plain-FK style of
`PreferenceProfile` rather than a JPA `@ManyToMany`.

## Critical Implementation Details

- **CSRF for HTMX (one-time wiring, load-bearing for S-05).** Spring's CSRF is
  on and pinned by `CsrfEnforcedTests`; HTMX POSTs send no token by default.
  Expose the token + header name as `<meta>` tags in the layout `<head>`
  (`th:content="${_csrf.token}"` / `${_csrf.headerName}`) and register a global
  `htmx:configRequest` listener that copies the token into the request headers.
  This is the canonical pattern S-05 inherits — do it in the shared layout, not
  per-button. (Switching to a cookie-based CSRF repository was explicitly
  rejected to avoid touching the pinned server-side CSRF config.)
- **Toggle activeness asymmetry (FR-013).** Marking is allowed only for an
  **active** resort (the control only renders on active rows, and the endpoint
  guards with `findByIdAndActiveTrue` → `404` on a mark of a missing/inactive
  resort). **Unmark must succeed regardless of active state** so a reference to a
  later-deactivated resort can always be cleared — resolve the resort for unmark
  with `findById` (or skip the resort lookup entirely and delete by
  `(userId, resortId)`).
- **Idempotency.** Mark uses an existence check before insert and treats an
  already-present row as a no-op (the `UNIQUE (user_id, resort_id)` constraint is
  the backstop, mirroring `AdminBootstrap` / profile-save handling of
  `DataIntegrityViolationException`). Unmark of a non-existent row is a no-op.

## Phase 1: Persistence — visited_resorts table, entity, repository

### Overview

Establish the storage for visited marks: a Flyway `V4` migration, the
`VisitedResort` JPA entity, and a repository with the queries this slice (and
S-05) need — verified on H2 and Postgres.

### Changes Required:

#### 1. Flyway migration

**File**: `src/main/resources/db/migration/V4__create_visited_resorts.sql`
(V3 is taken by `V3__create_preference_profiles.sql`; this is the next free
version).

**Intent**: Create the join table backing per-user visited marks. Forward-only,
portable across H2 (PG mode) and Postgres.

**Contract**: Table `visited_resorts` with `id BIGINT GENERATED BY DEFAULT AS
IDENTITY PRIMARY KEY`, `user_id BIGINT NOT NULL`, `resort_id BIGINT NOT NULL`,
`created_at TIMESTAMP NOT NULL`, and `CONSTRAINT uq_visited_user_resort UNIQUE
(user_id, resort_id)`. No `updated_at` (a mark is immutable — it exists or it
doesn't). DDL must mirror the style of `V1`–`V3` exactly.

#### 2. VisitedResort entity

**File**: `src/main/java/com/nextslope/visited/VisitedResort.java`

**Intent**: JPA mapping of a single visited mark, in a new `com.nextslope.visited`
package, following the entity convention.

**Contract**: `@Entity @Table(name = "visited_resorts")` with Lombok
`@Getter/@Setter/@NoArgsConstructor/@AllArgsConstructor/@Builder`. Fields: `Long
id` (IDENTITY), `Long userId` (`@Column(name="user_id", nullable=false)`), `Long
resortId` (`@Column(name="resort_id", nullable=false)`), `Instant createdAt`
(`@CreationTimestamp`, `nullable=false, updatable=false`). No `@UpdateTimestamp`.

#### 3. VisitedResortRepository

**File**: `src/main/java/com/nextslope/visited/VisitedResortRepository.java`

**Intent**: Spring Data repository exposing exactly the queries this slice and
S-05 need — kept minimal per the agreed read-model scope.

**Contract**: `extends JpaRepository<VisitedResort, Long>` with:
`boolean existsByUserIdAndResortId(Long userId, Long resortId)`;
a delete for unmark — `@Modifying @Transactional long deleteByUserIdAndResortId(Long userId, Long resortId)`
(or a derived `deleteBy…` returning the delete count);
and the S-05 read — a projection of visited resort ids for a user, e.g.
`@Query("select v.resortId from VisitedResort v where v.userId = :userId") Set<Long> findResortIdsByUserId(Long userId)`.

#### 4. Repository tests (dual-engine)

**File**: `src/test/java/com/nextslope/visited/VisitedResortRepositoryTests.java`
(H2 `@DataJpaTest`) and
`src/test/java/com/nextslope/visited/VisitedResortRepositoryPostgresTests.java`
(`@Testcontainers` real Postgres, mirroring `ResortRepositoryPostgresTests`).

**Intent**: Prove the migration + mapping load and the queries behave on both
engines: insert a mark; `existsByUserIdAndResortId` true/false; the unique
constraint rejects a duplicate `(user_id, resort_id)`; `deleteByUserIdAndResortId`
removes it and is a no-op when absent; `findResortIdsByUserId` returns only that
user's ids.

**Contract**: Follow the existing `*RepositoryTests` / `*RepositoryPostgresTests`
shape (annotations, Testcontainers Postgres setup). Assert the unique constraint
via a `DataIntegrityViolationException` on duplicate insert.

### Success Criteria:

#### Automated Verification:

- Migration applies cleanly on app/test boot: `./gradlew test`
- H2 repository slice passes: `./gradlew test --tests com.nextslope.visited.VisitedResortRepositoryTests`
- Postgres repository test passes: `./gradlew test --tests com.nextslope.visited.VisitedResortRepositoryPostgresTests`
- Full context still boots (entity↔schema validate): `./gradlew test --tests com.nextslope.NextslopeApplicationTests`

#### Manual Verification:

- `visited_resorts` table is visible in the H2 console with the expected columns
  and unique constraint after a local `./gradlew bootRun`.

**Implementation Note**: After automated verification passes, pause for manual
confirmation before Phase 2.

## Phase 2: Service, toggle endpoint, and privacy guarantee

### Overview

Add the owner-scoped service that marks/unmarks, the authenticated POST endpoint
that toggles and returns the updated control fragment, and the mandatory
two-user isolation test that proves the visited list is private.

### Changes Required:

#### 1. VisitedResortService

**File**: `src/main/java/com/nextslope/visited/VisitedResortService.java`

**Intent**: Owner-scoped mark/unmark/read, taking `userId` (never an arbitrary
mark id), mirroring `PreferenceProfileService`'s transactional, principal-scoped
shape. Encapsulates the active-on-mark / always-on-unmark asymmetry and
idempotency.

**Contract**:
- `@Transactional boolean toggle(Long userId, Long resortId)` — if a mark exists,
  delete it and return `false` (now unvisited); else verify the resort is active
  (`ResortRepository.findByIdAndActiveTrue`, throw a not-found signal if absent),
  insert a mark, return `true` (now visited). Treats a concurrent duplicate
  (`DataIntegrityViolationException`) as already-visited.
- `@Transactional(readOnly = true) Set<Long> visitedResortIds(Long userId)` —
  delegates to `findResortIdsByUserId`; the read S-05 reuses.

(No standalone `isVisited(userId, resortId)` method — it has no caller in this
slice; `toggle` returns the new state directly and the list renders from
`visitedResortIds`. Add it later only if a consumer actually needs it.)

Depends on `VisitedResortRepository` and `ResortRepository`.

#### 2. Shared current-user resolver (refactor)

**File**: `src/main/java/com/nextslope/user/CurrentUserService.java` (new), plus a
refactor of `web/ProfileController.java`.

**Intent**: This slice makes `findByEmail(EmailNormalizer.normalize(principal
.getUsername())) → getId()` the **third** copy of the principal→userId lookup
(after `ProfileController`, now `VisitedController` and `ResortController`). Rule
of three: extract it once instead of triplicating.

**Contract**: A `@Service`/`@Component` `CurrentUserService` (in
`com.nextslope.user`) depending on `UserRepository`, exposing
`Long requireUserId(UserDetails principal)` — the existing
`ProfileController.currentUserId` body verbatim (normalize email, `findByEmail`,
`getId`, throw `401` `ResponseStatusException(HttpStatus.UNAUTHORIZED)` when
absent). Refactor `ProfileController` to inject it and drop its private
`currentUserId`; `VisitedController` (§3) and `ResortController` (Phase 3 §3) use
the same bean. Update `ProfileControllerWebMvcTests` mocks accordingly (mock
`CurrentUserService` instead of `UserRepository` where the lookup was used).

> Note: this refactor touches `ProfileController` (outside the new `visited`
> package). It is intentionally in scope to avoid a third copy of the lookup;
> the only behavior change is delegation, so `ProfileControllerWebMvcTests` must
> swap its `UserRepository` stub for a `CurrentUserService` stub.

#### 3. VisitedController

**File**: `src/main/java/com/nextslope/web/VisitedController.java`

**Intent**: Authenticated POST toggle that resolves the current user from the
principal, flips visited state, and returns the single updated control fragment
for HTMX to swap in place.

**Contract**: `@PostMapping("/resorts/{id}/visited")` taking
`@AuthenticationPrincipal UserDetails principal`, `@PathVariable Long id`, and a
`Model`. Resolve `userId` via the shared `CurrentUserService.requireUserId(principal)`
(§2) — not a re-inlined `findByEmail` lookup. Call
`service.toggle`; on the resort-not-found/inactive signal respond `404`
(`ResponseStatusException(HttpStatus.NOT_FOUND)`, mirroring `ResortController`).
Put the resort id and the new `visited` boolean on the model under attribute
names that **exactly match the fragment parameters** — `resortId` and `visited`
(a parameterized fragment returned by name binds its parameters from context
variables of the same name, so an attribute named `id` would leave `resortId`
unbound). Alternatively pass them as explicit fragment args
(`visitedToggle(resortId, visited)`). Return a view that renders **both** the
`visitedToggle` control fragment **and** the `visitedRowState` out-of-band
row-highlight fragment (e.g. a thin `resorts/visited-toggle-response` template
that includes both fragments with explicit args, or a multi-fragment selector),
so one POST updates the button and the row highlight together. The route is
authenticated automatically by the existing security chain (no `SecurityConfig`
change) and must accept a CSRF token.

#### 4. Toggle control fragment

**File**: `src/main/resources/templates/resorts/list.html` (add a
`th:fragment="visitedToggle(resortId, visited)"`)

**Intent**: The single reusable control rendered both on initial list load and as
the POST response, so mark/unmark renders identically in both paths.

**Contract**: A `th:fragment="visitedToggle(resortId, visited)"` rendering a
button that POSTs to `/resorts/{id}/visited` via HTMX (`hx-post`,
`hx-swap="outerHTML"`, targeting itself), showing "Visited ✓" vs "Mark visited"
and a state class driven by `visited`. (Initial-render wiring into the table
lands in Phase 3; the fragment itself is defined here because it is the
endpoint's return contract.)

**Row highlight via out-of-band swap.** The control swap only replaces the
button, so the in-place row highlight is driven by a **second, out-of-band
element** in the same response: a tiny `th:fragment="visitedRowState(resortId,
visited)"` rendering the row's `<tr>` opening (or an empty placeholder element)
carrying `hx-swap-oob="true"` and a **stable id** `id="resort-row-${resortId}"`,
with the visited state class (`table-active`) applied iff `visited`. HTMX swaps
this OOB element by id independently of the targeted button, so a single POST
response updates both the button *and* the row highlight in place — no full
reload. The endpoint returns both fragments (see Phase 2 §3); the table in Phase
3 gives each `<tr>` the matching `id="resort-row-${r.id}"`.

#### 5. Controller test

**File**: `src/test/java/com/nextslope/web/VisitedControllerWebMvcTests.java`

**Intent**: Pin the endpoint's contract: toggle on/off, CSRF required, anonymous
redirected, 404 on unknown resort.

**Contract**: `@WebMvcTest(controllers = VisitedController.class)` +
`@Import({SecurityConfig.class, AppUserDetailsService.class})`, `@MockitoBean`
`VisitedResortService` + `CurrentUserService` (and `UserRepository` /
`ResortRepository` if the security import pulls them in, per `CsrfEnforcedTests`).
Stub `currentUserService.requireUserId(...)` to return a fixed userId. Cases:
anonymous POST →
redirect `/login`; `@WithMockUser` POST `.with(csrf())` returns `200` + the
`visitedToggle` fragment and calls `service.toggle(userId, id)`; POST **without**
csrf → `403`; a `toggle` that signals not-found → `404`.

#### 6. Two-user isolation integration test (privacy guardrail)

**File**: `src/test/java/com/nextslope/visited/VisitedResortOwnershipIntegrationTests.java`

**Intent**: Prove the PRD privacy guardrail — a user's visited list is visible to
and mutable by only that user; an admin cannot see it; one user's marks never
affect another's. Specializes the `assertWrongOwnerDenied` / ownership seam named
in `OwnershipPatternIntegrationTests`.

**Contract**: `extends TwoUserIntegrationTestBase`; seed a couple of active
resorts (as `PreferenceProfileOwnershipIntegrationTests` does). User A POSTs a
mark on resort X (session A, `.with(csrf())`); assert via the repository that
exactly A's row exists and `findResortIdsByUserId(B)` is empty. Assert the admin's
`visitedResortIds` is empty (no admin visibility). Because the route is
principal-scoped (no user id in the path), there is no cross-user URL to forge —
the assertion is **isolation** (the same shape as
`PreferenceProfileOwnershipIntegrationTests`), not a forbidden response.

**On the `assertWrongOwnerDenied` seam (by design, not an oversight):**
`OwnershipPatternIntegrationTests` and `AccessControlAssertions.assertWrongOwnerDenied`
name S-04 as a candidate to specialize the wrong-owner seam, but S-04
deliberately exposes **no addressable cross-user route** — so there is nothing to
assert a forbidden cross-user response against. This slice therefore proves the
guardrail via isolation and **intentionally leaves the seam a delegating
placeholder**; do not force a synthetic wrong-owner assertion here. (A real
specialization waits for a slice that introduces an id-addressable owned route.)

### Success Criteria:

#### Automated Verification:

- Controller test passes: `./gradlew test --tests com.nextslope.web.VisitedControllerWebMvcTests`
- Isolation test passes: `./gradlew test --tests com.nextslope.visited.VisitedResortOwnershipIntegrationTests`
- CSRF stays enforced (no regression): `./gradlew test --tests com.nextslope.CsrfEnforcedTests`
- Full suite green: `./gradlew test`

#### Manual Verification:

- `curl`/HTTPie a POST to `/resorts/{id}/visited` with a valid session + CSRF

**Implementation Note**: After automated verification passes, pause for manual
confirmation before Phase 3.

## Phase 3: Browse-list UI + HTMX wiring

### Overview

Surface the control on every active resort row, wire the one-time CSRF-token
delivery to HTMX (reused by S-05), and make the mark/unmark swap in place with a
visited-row highlight.

### Changes Required:

#### 1. CSRF token delivery to HTMX (one-time, shared)

**File**: `src/main/resources/templates/fragments/layout.html`

**Intent**: Make every HTMX POST carry the CSRF token, since Spring CSRF is on and
pinned. This is the canonical wiring S-05 inherits.

**Contract**: Add two `<meta>` tags to the `head(title)` fragment —
`name="_csrf"` `th:content="${_csrf.token}"` and `name="_csrf_header"`
`th:content="${_csrf.headerName}"`. In the `scripts` fragment, add a small inline
script registering a `htmx:configRequest` listener that reads the two metas and
sets `evt.detail.headers[headerName] = token`. No change to `SecurityConfig`.

#### 2. List table: visited column + initial render

**File**: `src/main/resources/templates/resorts/list.html`

**Intent**: Add a per-row action cell that renders the `visitedToggle` fragment in
its correct initial state, and a row highlight when visited.

**Contract**: Add a "Visited" `<th>` (update the empty-state `colspan` from 6 to
7). Give each `th:each` row a stable `id="resort-row-${r.id}"` so the
`visitedRowState` out-of-band swap can target it. Render
`visitedToggle(r.id, visitedIds.contains(r.id))` in the row's action cell and
apply the `table-active` row class when `visitedIds.contains(r.id)`. On toggle,
the control's `hx-swap="outerHTML"` replaces just the button while the response's
`hx-swap-oob` `visitedRowState` element (matched to `resort-row-${r.id}`) updates
the row highlight in place — both without a full reload.

#### 3. Pass visited ids to the list view

**File**: `src/main/java/com/nextslope/web/ResortController.java`

**Intent**: The list handler must know which resorts the current user has visited
to render initial state.

**Contract**: `ResortController.list` gains `@AuthenticationPrincipal UserDetails
principal`, resolves `userId` via the shared `CurrentUserService.requireUserId(principal)`
(Phase 2 §2), and adds `model.addAttribute("visitedIds",
visitedResortService.visitedResortIds(userId))`. Inject `VisitedResortService`
and `CurrentUserService` into the controller. Update `ResortControllerWebMvcTests`
for the new model attribute + the `VisitedResortService` / `CurrentUserService`
mocks.

#### 4. Row-highlight styling

**File**: existing CDN Bootstrap classes (no new CSS file unless needed)

**Intent**: A subtle, accessible "this row is visited" cue.

**Contract**: Use a Bootstrap row state class (`table-active`/`table-success`
subtle variant) toggled by `visited`. If a custom rule is needed, add it to a
small static stylesheet under `src/main/resources/static/css/` and link it via
the layout (the `/css/**` path is already permit-listed in `SecurityConfig`).

### Success Criteria:

#### Automated Verification:

- Updated controller test passes: `./gradlew test --tests com.nextslope.resort.ResortControllerWebMvcTests`
- Full suite green: `./gradlew test`

#### Manual Verification:

- On `/resorts`, every active row shows a "Mark visited" button; clicking it
  flips to "Visited ✓" and highlights the row **without a full page reload**.
- Clicking again unmarks it in place.
- The marked state survives a hard browser refresh (persisted).
- Signing in as a different user shows none of the first user's marks.
- No CSRF `403` errors in the browser network tab on toggle.

## Testing Strategy

### Unit / slice tests:

- `VisitedResortRepositoryTests` (`@DataJpaTest`, H2): mark/exists/delete/unique
  constraint/`findResortIdsByUserId`.
- `VisitedResortRepositoryPostgresTests` (`@Testcontainers`): same on real
  Postgres (prod-engine proof; CI-gated).
- `VisitedControllerWebMvcTests` (`@WebMvcTest`): toggle on/off, CSRF required,
  anonymous → `/login`, `404` on unknown resort, returns the `visitedToggle`
  fragment.
- Update `ResortControllerWebMvcTests` for the `visitedIds` model attribute.

### Integration tests:

- `VisitedResortOwnershipIntegrationTests` (`TwoUserIntegrationTestBase`):
  per-user isolation — A's marks invisible to B and to the admin; B's account
  unaffected by A.

### Manual testing steps:

1. Sign in, go to `/resorts`, mark a resort → row highlights, button flips, no
   reload.
2. Unmark it → reverts in place.
3. Hard-refresh → state persists.
4. Sign in as a second user → no marks visible.
5. Inspect the network tab → POST carries the CSRF header, no `403`.

## Performance Considerations

Negligible at MVP scale (≤40 resorts, small user base). The list handler does one
extra `findResortIdsByUserId` query per page load; each toggle is one
exists/insert or one delete. No N+1 (visited ids fetched once as a `Set`).

## Migration Notes

`V4__create_visited_resorts.sql` is forward-only and additive — no change to
`users`/`resorts`/`preference_profiles`. Existing data is untouched.
Account-deletion cascade of these rows is S-07's responsibility, not this slice's.
