# Research: S-07 Account deletion — codebase readiness

**Date**: 2026-07-02T00:00:00+02:00
**Researcher**: binieckw
**Git Commit**: e7ea3f76ac16a09d4552d680543a271456832330
**Branch**: main
**Repository**: NextSlope

## Research Question

What does the live codebase already provide, and what is missing, to implement roadmap slice
**S-07 `account-deletion`**: a signed-in user permanently deletes their own account; once confirmed,
their **preference profile** (FR-004) and **visited list** (FR-005) are immediately removed and
never reappear on any product surface; deletion is **immediate — no undo window** (roadmap Open
Question 4). (PRD refs: FR-004, FR-005, and the "permanently delete account" NFR at `prd.md:144`.)

## Summary

S-07 is a **small, principal-scoped slice with one load-bearing detail: the delete must cascade in
the application layer, in the right order, because the schema has no `ON DELETE CASCADE`.** Almost
everything else is precedented and copyable.

- **The three tables that hold a user's data are known and small:** `users` (1 row),
  `preference_profiles` (0–1 row, `UNIQUE(user_id)`) plus its element-collection child
  `preference_profile_regions`, and `visited_resorts` (0–n rows). No other table references a user.
- **There is NO database-level cascade.** `preference_profiles.user_id` has a plain FK to `users`
  **without `ON DELETE CASCADE`** (`V3`), and `preference_profile_regions` has a FK to
  `preference_profiles` **without cascade** (`V3`). `visited_resorts` has **no FK to `users` at all**
  (`V4` — bare `user_id`). So a naive `userRepository.delete(user)` while a profile exists throws a
  FK-violation. Deletion order must be **visited → profile (via entity delete, so its regions go
  first) → user**, inside one `@Transactional` service.
- **The session/auth aftermath is already 90% solved.** `StaleAuthenticatedSessionFilter` was built
  *for this slice* — its javadoc literally cites "the backing account is deleted (S-07)" — and
  `StaleSessionIntegrationTests` already proves that after the user row is gone, gated pages redirect
  to `/login` and the home page renders signed-out. The plan should still **explicitly invalidate the
  deleting user's own session** on success (clean redirect to the public landing) rather than relying
  only on the next request self-healing.
- **No account/settings surface or delete route exists yet.** There is no `/account` page and no
  "Delete account" control anywhere. The natural home is the existing `/profile` page (a "danger
  zone" block) or a small new `/account` page; the delete itself is a **CSRF-protected POST** to a
  new route, never a GET.
- **Every reusable pattern already exists:** principal-scoped controller (`CurrentUserService`
  resolves the id — no id in the path, so no IDOR surface), POST + auto-injected CSRF token,
  post-action redirect with a query-param banner (the `?logout` precedent on `index.html`), and the
  full two-user integration + dual-engine (H2 + Testcontainers Postgres) test scaffolding. There is
  **no `AccountService` / `UserService` yet** — the delete orchestration is net-new.
- **The one genuine open decision is where the cascade lives:** application-level orchestration
  (**no new migration**, matches the app's "plain `Long` FK, app owns integrity" convention) vs. a
  new `V5__` migration adding `ON DELETE CASCADE`. Application-level is recommended and lower-risk.

## Detailed Findings

### A. The data a user owns — exactly three tables

| Table | Rows per user | Link to user | FK to `users`? | Cascade? |
|---|---|---|---|---|
| `users` | 1 | PK `id` | — | — |

### B. The cascade — the load-bearing detail

Because there is no DB-level cascade, deletion is an application-layer orchestration. **Correct
order** (children before parents):

1. `visited_resorts` by `user_id` — unconstrained (no FK), safe in any order.
2. `preference_profiles` for the user — **via the JPA entity** (`findByUserId(...)` →
   `repository.delete(entity)`), so Hibernate deletes the `preference_profile_regions` rows first,
   then the profile row.
3. `users` row — now free of referencing children.

**Critical gotcha for the plan/implementation.** Do **not** add a derived
`deleteByUserId(...)` to `PreferenceProfileRepository` and call it. Spring Data turns a derived
delete into a **bulk `DELETE` that neither loads the entity nor cascades to the element-collection
table**, so it violates `fk_preference_profile_regions_profile` (orphaned region rows). The
element collection is only cleaned up when the profile is removed as a **managed entity**
(`delete(entity)`), or by a bulk delete of `preference_profile_regions` *first* — the entity path is
simpler and portable. (Contrast: `VisitedResortRepository` already has a safe derived bulk delete,
`deleteByUserIdAndResortId`, because `visited_resorts` has no child table.)

Repositories today expose the finders the cascade needs, and lack the by-user deletes:
```7:12:src/main/java/com/nextslope/user/UserRepository.java
public interface UserRepository extends JpaRepository<User, Long> {

	Optional<User> findByEmail(String email);

	boolean existsByEmail(String email);
}
```
```7:10:src/main/java/com/nextslope/profile/PreferenceProfileRepository.java
public interface PreferenceProfileRepository extends JpaRepository<PreferenceProfile, Long> {

	Optional<PreferenceProfile> findByUserId(Long userId);
}
```
```11:22:src/main/java/com/nextslope/visited/VisitedResortRepository.java
public interface VisitedResortRepository extends JpaRepository<VisitedResort, Long> {

	boolean existsByUserIdAndResortId(Long userId, Long resortId);

	@Modifying
	@Transactional
	long deleteByUserIdAndResortId(Long userId, Long resortId);

	/** The S-05 read: ids of the resorts a given user has marked visited. */
	@Query("select v.resortId from VisitedResort v where v.userId = :userId")
	Set<Long> findResortIdsByUserId(@Param("userId") Long userId);
}
```
Likely net-new: `VisitedResortRepository.deleteByUserId(Long)` (safe bulk delete),
`UserRepository.delete(...)`/`deleteById(...)` (inherited), and a `@Transactional`
`deleteAccount(userId)` orchestrator on a **new `AccountService`** (or `UserService`) in
`com.nextslope.user`. Keep the orchestration in a service, not the controller (matches
`PreferenceProfileService` / `VisitedResortService`).

### C. Session & auth aftermath — already scaffolded for S-07

`StaleAuthenticatedSessionFilter` runs before the authorization filter and logs out any
authenticated session whose principal no longer maps to a persisted user — it was written with
account deletion as its motivating case:
```20:32:src/main/java/com/nextslope/config/StaleAuthenticatedSessionFilter.java
/**
 * Invalidates an authenticated session whose principal no longer maps to a persisted user.
 *
 * <p>Such a stale session arises when the backing account is deleted (S-07) or the database is
 * reset in development while the browser keeps a still-valid session cookie. ...
 */
```
It is wired into the main chain (`SecurityConfig.filterChain`, `addFilterBefore(..., AuthorizationFilter.class)`),
and `StaleSessionIntegrationTests` already asserts the post-deletion behavior (gated → `/login`,
home → signed-out) after a bare `userRepository.deleteAll()`:
```24:42:src/test/java/com/nextslope/StaleSessionIntegrationTests.java
	@Test
	void gatedPageRedirectsToLoginWhenSessionUserNoLongerExists() throws Exception {
		MockHttpSession session = loginAsUserA();
		userRepository.deleteAll();

		mockMvc.perform(get("/resorts").session(session))
				.andExpect(status().is3xxRedirection())
				.andExpect(redirectedUrl("/login"));
	}
```

**Implication:** the deletion flow is *safe* even if it does nothing about the current session — the
very next request self-heals. But for a clean UX the delete handler should **proactively invalidate
the caller's own session** and redirect to the public landing, mirroring the sign-out contract
("Sign-out returns the user to a public landing surface", `prd.md:165`). The primitives already used
in-repo: `SecurityContextLogoutHandler` (used by the stale filter) or
`request.getSession().invalidate()` + `SecurityContextHolder.clearContext()`. Note that after
invalidation a flash attribute won't survive — signal success via a **redirect query param** and an
`th:if="${param.deleted}"` banner, exactly like the existing `?logout` pattern:
```16:19:src/main/resources/templates/index.html
				<div th:if="${param.logout}" class="alert alert-success" role="alert">
					You've been signed out.
				</div>
```

### D. UI / controller / form conventions to mirror

**Principal-scoped controller, no id in path (so no IDOR surface).** Every user-owned handler
resolves the id from the principal via `CurrentUserService.requireUserId(principal)`:
```21:26:src/main/java/com/nextslope/user/CurrentUserService.java
	/** The persistent id of the authenticated user, or {@code 401} when no matching user row exists. */
	public Long requireUserId(UserDetails principal) {
		User user = userRepository.findByEmail(EmailNormalizer.normalize(principal.getUsername()))
				.orElseThrow(() -> new ResponseStatusException(HttpStatus.UNAUTHORIZED));
		return user.getId();
	}
```
`ProfileController`, `VisitedController`, and `RecommendController` all follow this shape — the delete
controller should too (`@AuthenticationPrincipal UserDetails principal` → `requireUserId`).

**Destructive action must be POST + CSRF.** CSRF is enabled and pinned repo-wide; Thymeleaf
`th:action` POST forms auto-inject the token, and HTMX requests get it via the `<meta>`-tag wiring in
`fragments/layout.html`. Existing state-changing controls (sign-out in the navbar, profile save, the
visited toggle) are all POST forms. The delete route must be a POST; a GET delete would be
CSRF-bypassable and pre-fetchable.

**Confirmation is required by the NFR** ("once deletion is confirmed …", `prd.md:144`) and the
no-undo decision. There is **no modal/confirm pattern in the repo yet** — the plan chooses the
affordance: a dedicated confirm step/page, a Bootstrap modal, or a typed-confirmation field. Keep it
server-rendered (no JS build step — see Hard Rules).

**Where the control lives.** The navbar (`fragments/layout.html`) has Profile + Sign-out; the
`/profile` page (`profile/form.html`) is the natural home for a "Danger zone → Delete account" block,
or add a small new `/account` page. There is currently no account/settings route.

### E. Test scaffolding & conventions

- **Two-user / integration base:** `TwoUserIntegrationTestBase` (`@SpringBootTest` +
  `@AutoConfigureMockMvc`) seeds users A/B/admin and gives `loginAsUserA()` etc. returning a live
  `MockHttpSession`. **Caveat for S-07 tests:** its `@AfterEach clearFixtureUsers()` does
  `userRepository.deleteAll()`, which will hit the `preference_profiles` FK if a profile row survives
  the test. JUnit runs the **subclass `@AfterEach` before the superclass's**, so — exactly as
  `PreferenceProfileOwnershipIntegrationTests` does — S-07 tests must clear their profile/visited rows
  in their own `@AfterEach` (or the delete-under-test already removed them).
- **Dual-engine persistence proof (the repo standard):** `@DataJpaTest` on H2 **and**
  `@SpringBootTest @Testcontainers` on real Postgres 16 for the cascade correctness (e.g. mirror
  `PreferenceProfileRepositoryTests` + `PreferenceProfileRepositoryPostgresTests`,
  `VisitedResortRepositoryTests` + `...PostgresTests`). This is where the FK-order / element-collection
  cleanup is actually proven — H2 alone will not catch a Postgres FK-ordering bug.
- **Controller slice:** `@WebMvcTest(controllers = X.class)` + `@Import({SecurityConfig.class,
  AppUserDetailsService.class})` + `@MockitoBean` collaborators, `.with(csrf())` on the POST, and
  stub `userRepository.existsByEmail(...) → true` so `StaleAuthenticatedSessionFilter` lets the
  request through.
- **CSRF enforcement:** `CsrfEnforcedTests` is the template proving a POST without a token is
  rejected — extend it (or assert in the slice test) for the delete route.
- **Permit-list lock:** `PermitListLockTests.mustStayGatedPathsRedirectAnonymousToLogin` enumerates
  gated routes — add the new delete/account route so an accidental `permitAll()` widening fails CI:
```87:96:src/test/java/com/nextslope/PermitListLockTests.java
	@ParameterizedTest
	@ValueSource(strings = {"/error", "/profile", "/visited", "/recommend", "/admin", "/resorts", "/resorts/1"})
	void mustStayGatedPathsRedirectAnonymousToLogin(String path) throws Exception {
		...
		mockMvc.perform(get(path))
				.andExpect(status().is3xxRedirection())
				.andExpect(redirectedUrl("/login"));
	}
```
- **Session-after-delete:** reuse the `StaleSessionIntegrationTests` shape for the end-to-end flow
  (log in → delete → assert rows gone → assert next gated request redirects to `/login`, home shows
  signed-out).
- **PIT mutation gate** is scoped to `com.nextslope.recommendation.*` only (`build.gradle`), so the
  new `user`/account code is **not** mutation-gated — conventional slice + integration tests suffice.

### F. Privacy guardrail — "does not reappear on any product surface"

The surfaces that read a user's profile/visited data are all principal-scoped by `userId`:
`GET /profile` (profile), `GET /resorts` + `POST /recommend` (visited via `VisitedResortService`,
profile via `PreferenceProfileService.snapshotForUser`). Once the rows and the user are gone, there
is nothing left to render — and **no admin surface reads user profile/visited data** (none exists;
that would be S-06, and the PRD forbids admin visibility into profiles/visited, `prd.md:142`). So the
guardrail is satisfied by the cascade itself; there is no separate "hide from admin" work. The
recommendation candidate pool reads resorts, not users, so it is unaffected.

## Architecture Insights

- **The schema deliberately owns integrity in the app, not the DB, for user-scoped data.** Visited
  rows carry a bare `user_id` with no FK; the profile FK has no cascade. That is consistent with the
  codebase convention (plain `Long` foreign keys, `@ManyToOne` avoided "to keep the entity lean").
  S-07 should honor that by cascading in a `@Transactional` service rather than retrofitting DB
  cascade — the app is already the source of referential-integrity truth for these tables.
- **S-07's hardest part was pre-built in S-01.** `StaleAuthenticatedSessionFilter` +
  `StaleSessionIntegrationTests` mean a deleted account never leaves a usable session anywhere; the
  slice mostly wires the delete action and its own-session invalidation on top of that safety net.
- **No new domain model, no new axis.** Unlike S-06/S-08, S-07 adds no entity/column — it removes
  rows. If the plan keeps the cascade in the application layer, `ddl-auto=validate` stays green with
  **no new migration**.
- **Layered convention holds:** new `AccountService.deleteAccount(userId)` (`@Transactional`) +
  by-user delete finders + a thin principal-scoped controller returning a redirect. Confirmation and
  session-invalidation are the only genuinely new UI/security behaviors.

## Open Questions

1. **Where does the cascade live (must resolve at planning)?** (a) **Application-level** — a
   `@Transactional deleteAccount(userId)` deletes visited (bulk by user), then the profile *as a
   managed entity* (regions go with it), then the user. **No new migration**, matches the app's
   integrity-in-app convention. **Recommended.** (b) **DB-level** — a `V5__` migration adding
   `ON DELETE CASCADE` to `fk_preference_profiles_user_id` and `fk_preference_profile_regions_profile`
   (and possibly a new FK on `visited_resorts`), then `userRepository.delete(user)` cascades. More DDL,
   must be portable across H2 + Postgres, forward-only — heavier for little gain here.
2. **Where does the "Delete account" control live?** Reuse `/profile` (a "Danger zone" block) vs. a
   new `/account`/settings page. `/profile` is the smallest change; `/account` is cleaner if more
   account controls are expected. (No account/settings surface exists today.)
3. **Confirmation affordance.** Dedicated confirm page, Bootstrap modal, or typed-confirmation field
   (e.g. type your email). Must be server-rendered (no JS build step). The NFR requires *some*
   explicit confirmation; the exact form is a UX call.
4. **Own-session handling on success.** Explicitly invalidate the caller's session + redirect to the
   public landing with a `?deleted` banner (recommended, mirrors sign-out), vs. relying solely on
   `StaleAuthenticatedSessionFilter` to clean up on the next request. Also decide the post-delete
   destination (`/` landing vs. `/login`).
5. **Admin/self-deletion edge cases.** Can an ADMIN delete their own account (risk: deleting the last
   admin)? PRD has no multi-admin management in v1 and admin creation is out-of-band via
   `AdminBootstrap`, so the simplest v1 answer is "same self-delete flow applies to everyone"; confirm
   whether any last-admin guard is wanted (likely out of scope).
